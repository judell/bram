# Bram chooses the session; nothing else names it

Status: decided 2026-10-27 · revisit when a CLI changes how it names or resumes sessions, or a fourth agent arrives

**Question:** With three agents (Claude, Codex, OpenCode) and sessions paired across them, who decides which session a switch, reload or New session is about?

**Decision:** Bram chooses the session, launches it by id, marks it current at launch, and groups sessions only through an explicit act tied to that id. Nothing in session switching takes a CLI's own "most recent", a cached guess, or a "file created inside a time window" as the identity of a session.

**Groups, not pairs (2026-10-28, `session-groups`).** A line of work is a *group*: at most one session per agent, any number of agents, and a session is in at most one group. Switching agents from a member resumes that agent's member, by id. With three agents a team was three pairs, and pairs could disagree (two members paired with a third but not with each other); with four it would be six. The explicit act is now **Add it to '<group>'** on the offer (or New session for the agent), and a session leaves with **Leave** on its Sessions row. Pairs still holding when groups shipped were converted once (`op=group-migrate`); where a merge would put two sessions of one agent in a group, the newer pair won. Catch-up follows: arriving in a member offers what *every other member* did since this session last caught up on it, counted per (reader, source), so catching one member up marks nothing read for another. Members share the group's name: joining renames a session to it (no "(Codex)"-style tag), and a grouped session can be renamed only after it leaves, so the Sessions row lists agents, not titles. **A switch never lands in another group's session** (2026-10-28 04:00Z: a switch from a new group fell back to the burndown group's OpenCode session, and one click on the offer moved and renamed it). From a group, the target agent's member is resumed, or a new session is started for the group. From a loose session, the target's most recent *loose* session is resumed with the offer, or a new one is started when all are grouped. Joining is explicit: the offer's Group these two, or a loose row's Add to '<group>'. A resume across agents no longer joins.

**Alternatives:**

- *Let each CLI choose (`--continue`, `--last`).* Rejected: the CLI's "most recent" and Bram's diverge (OpenCode orders by its own update time, Claude by file mtime with Bram's hysteresis), and the user acts on what Bram shows.
- *Infer identity from timing* (a session file created within 2 s of a request; the first session change after a launch). Rejected as the deciding signal: CLIs rewrite session files at exit, and reloads produce session changes. Both defeated it on the day. Timing may still narrow a choice Bram has already made; it never makes one.
- *Make pairing automatic on every switch.* Already rejected on 2026-10-04 (`e311c09`): an automatic pair undid the user's Unpairs. This decision keeps pairing explicit and adds that the explicit act must be tied to a known id.

**Known gaps (recorded, not filed):**

- No way to add an arbitrary existing session to a group; resume it first, then Add. A cross-agent resume from the Sessions list joins the resumed session to the group being left only when it is in no group itself.
- `opencode session delete` is untested on Windows, where an npm `opencode.cmd` shim may not resolve from `Command::new("opencode")`.
